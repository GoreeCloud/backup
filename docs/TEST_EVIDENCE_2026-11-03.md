# GoreeCloud Backup — verified development evidence (2026-11-03)

**Stage:** development alpha, not a stable release, not deployed. This file distinguishes local verification from GitHub publication and CI results. The service remains a development alpha, not a deployed or stable product.

## Source and quality checks

Executed against the source package on a Linux amd64 Go 1.23.2 environment:

```sh
go test -race ./...
go vet ./...
go build ./cmd/goreecloud-backup
```

All commands completed with exit status 0 after adding admission, preview and restore safety tests. Tests use fake engine executors to validate API/command behavior; they do not verify Kopia encryption or restore integrity. The dashboard JavaScript also passed `node --check`, and the optional isolated-Rclone smoke script passed `bash -n`.

An additional **real local server-process smoke test** launched the built Linux binary bound to `127.0.0.1` with a disposable random token. It verified that the dashboard and CSP are served, unauthenticated `/api/v1/health` receives HTTP 401, authenticated health receives HTTP 200, and an invalid sync request receives HTTP 422. The service was stopped afterward. No engine binaries were available in that first sandbox; an independent real engine-through-API acceptance run was subsequently completed on an authorized Linux laptop (see below).

## Real transfer smoke test

Tested on an authorized Linux workstation using the installed Rclone 1.75.2 binary with an isolated disposable local source and destination. Operations used `--config /dev/null` and did not access configured cloud storage or personal files.

1. `rclone copy --immutable` from the test source to an empty test destination: completed.
2. `rclone check` of the copied file: **0 differences, 1 matching file**.
3. Added a destination-only test file and ran `rclone sync --dry-run`: output identified the would-be deletion; test confirmed the extra file still existed.
4. Ran `rclone sync` only within the isolated disposable destination: extra test file was deleted, copied file matched the original, and a second `rclone check` reported **0 differences, 1 matching file**.
5. Removed the dedicated temporary acceptance directory.

**Host-specific observation:** the Snap-packaged Rclone could not access a test path under `/tmp` because of packaging confinement. The same test succeeded within the authorized account's home directory. This is not a GoreeCloud Backup application bug, but should be reflected in packaging and onboarding.

## Signed Kopia encrypted-backup acceptance

Tested on the authorized Linux laptop in a dedicated temporary directory using official Kopia **v0.23.1**:

1. Downloaded the upstream `kopia-0.23.1-linux-x64.tar.gz`; its SHA-256 (`416d0f84a3dbb321a8b2d8f0997b1a0a6e915babe79ee76fa6e4d2bd1e1c5178`) matched the official checksum list and Kopia's upstream Homebrew formula.
2. Verified the detached `checksums.txt.sig` signature with an isolated GPG keyring and the Kopia Builder key fingerprint `7FB99DFD47809F0D5339D7D92273699AFD56A556`, consistent with Kopia's published installation documentation. GPG reported a good signature; third-party identity is grounded in the independently inspected published fingerprint, not the local keyring trust database.
3. Inspected archive entries and executable type, then invoked its self-reported `0.23.1` version. No system-wide installation occurred.
4. Created a filesystem repository with a fresh random test password, using Kopia's AES256-GCM-HMAC-SHA256 encryption, an isolated configuration and cache, and two disposable fixture files.
5. Created a snapshot in JSON mode and confirmed snapshot listing returned **1** record; retrieved the root object ID from `rootEntry.obj`.
6. Reserved a private restore destination and invoked the same no-overwrite and atomic-file flags generated by the GoreeCloud Backup API. Kopia reported **2 restored files and 2 directories**. A recursive directory comparison and SHA-256 comparison matched the original fixture data.
7. Ran `snapshot verify --verify-files-percent=100`; it processed **4 objects, 2 files, 67 bytes** without error. A search for the fixture text found no plaintext in the repository storage.
8. Confirmed the entire disposable test directory, including the downloaded binary and test repository, was removed; no production data or storage destinations were accessed.

This proves encrypted local backup/restore behavior **directly through the Kopia CLI** on that host. Separate combined application-to-engine acceptance was subsequently completed (see below). A plaintext-marker search is not a cryptographic security audit.

## End-to-end application API with real engines

On November 3, 2026, an authorized Linux laptop built the exact published `main` Go source and started the GoreeCloud Backup management service on an ephemeral loopback port with a random bearer token. Kopia 0.23.1 was downloaded from the official release and its archive matched the pinned upstream SHA-256. An isolated Kopia configuration, cache, encrypted local repository and disposable source directory were used; Rclone 1.75.2 was run only on local test paths.

1. Authenticated health endpoint reported both engines; unauthenticated access returned HTTP 401.
2. `POST /api/v1/jobs` performed a real Kopia snapshot backup; snapshot listing returned its root object ID; authenticated restore recovered the source files to a new protected destination and their bytes matched the originals.
3. The management API performed Rclone `copy` and `check`. Sync without the required typed confirmation returned HTTP 422.
4. The API sync preview completed successfully without removing a destination-only test file. A confirmed sync removed only the disposable destination-only file. A second sync attempting to reuse the same preview returned HTTP 409. A final `check` passed.
5. The service was stopped and its disposable directory, local repository, credentials, binaries and files were removed. This workflow never touched real backup repositories or cloud remotes.

The initial run failed at Rclone `copy` when the disposable workspace was a **hidden** home-directory folder: confined Snap Rclone denied access. Repeating the run in a **non-hidden** home-directory folder passed. This is a packaging integration concern requiring onboarding checks, not a reason to disable confinement.

Finally, the **published** `scripts/smoke-api-e2e.py` runner was executed independently using a checksum-verified Kopia archive and installed Rclone. It printed `PASS: authenticated API + Kopia snapshot/restore + Rclone copy/check/preview/sync` and exited successfully. Its temporary directories and server process were cleaned up. This provides repeatable local integration evidence; it does not establish production, cloud-provider, or cross-platform readiness.

## Opt-in private status journal acceptance

The job-status journal was added to the public repository at commit [`02c5d03493b46fba01efefb2e4f7bbd26c9a0953`](https://github.com/GoreeCloud/backup/commit/02c5d03493b46fba01efefb2e4f7bbd26c9a0953), with changes to the Go service, command initialization, journal implementation and unit tests. `go test -race ./...`, `go vet ./...` and `go build ./cmd/goreecloud-backup` passed locally after those changes.

Unit tests verified that the opt-in journal is atomic and mode `0600`, contains no secret token, source/destination paths or engine output, and restores a completed job's metadata after service reinitialization. They verified that an unfinished job is marked `interrupted` on restart, corrupt or overly permissive state is rejected, and old preview records cannot authorize a deletion-capable sync after restart.

A separate **real-process** test executed the **published** `scripts/smoke-api-e2e.py` on the authorized Linux laptop with `GOREECLOUD_BACKUP_STATE_DIR` set to a private, disposable directory. Kopia 0.23.1 was checksum-verified before use and Rclone used local test paths only. All eight authenticated engine operations completed, and the resulting state file was mode `0600`, schema 1, containing exactly eight `completed` job records with no engine output, source/destination path fields or fixture text. The server was stopped and test directories removed.

GitHub Actions [Verify run 41653767437](https://github.com/GoreeCloud/backup/actions/runs/41653767437) concluded `success` for the initial source and documentation changes relating to the opt-in journal. Later documentation-only commits and the current branch head must be evaluated separately.

**Limitations:** Journal status recovery does not resume, cancel or replay jobs; no durable schedule, migration support, encrypted at-rest metadata store, protected remote access, or production-readiness claim is established. Journal-write failures after admission are logged and reflected in health but cannot undo an already-running engine process. Do not equate a `completed` engine command with independent restored-data verification for real production datasets.

## Repository corruption negative test and Kopia cache isolation — local Linux

An additional isolated Linux experiment using the official, checksum- and
signature-verified Kopia 0.23.1 binary created a disposable encrypted
filesystem repository and backed up a 2 MiB uncompressible fixture. Initial
`snapshot verify --verify-files-percent=100` passed. After changing one
byte inside the largest encrypted content pack, the **same warmed-cache**
verification **still returned exit 0**. Repeating with a separate, empty
cache via `KOPIA_CACHE_DIRECTORY` returned **exit 1**, with a content
authentication/checksum error. This reproduced a local content-cache
false-negative, not an attack on production data.

To avoid this failure mode, GoreeCloud Backup now creates a fresh private
verification cache for both structural and full checks, never clears the
original cache, and removes the temporary cache on engine completion.
Go unit tests verify the override, cleanup on success and failure, fail-closed
temp creation, preservation of normal commands, and API-token filtering.

An independent **real API negative test** executed
`scripts/smoke-cache-isolation.py` with the patched Go server, a disposable
repository, and Kopia 0.23.1. It verified clean repository success, modified
one encrypted content-pack byte within the test repository, then confirmed
the authenticated `verify-full` job **failed**. The test asserted the
bounded API output and private status journal omitted the bearer token and
source path; its temporary files were removed. Result:

`PASS: clean encrypted repository verification completed`

`PASS: corrupted disposable content pack detected through API`

`PASS: failed job status, bounded output and private journal`

The test exited **0**, meaning the anticipated *failure detection* occurred.
This is not cloud backend acceptance, a repair feature, proof of fault
resilience on every platform, or a substitute for an independent restore.
See official Kopia documentation: https://kopia.io/docs/advanced/caching/
and https://kopia.io/docs/advanced/consistency/.

## UTC schedule claim crash/restart drill — separate process, real Kopia

On November 3, 2026, an authorized local Linux acceptance run executed
`scripts/smoke-scheduler-crash.py` against a fresh private encrypted
filesystem repository using the previously checksum- and GPG-signature-
verified official Kopia 0.23.1 binary. The script launched a loopback API
and a separate one-shot scheduler configured with one explicitly enabled
due UTC policy. The local Kopia command wrapper delayed execution to
reproduce an active job safely.

The test confirmed the scheduler had **already fsynced the claimed UTC
slot** while the authenticated API had a **running** snapshot job, then
deliberately killed only the scheduler process. A new one-shot scheduler
process reopened the private ledger, marked the previous claim as
`interrupted`, and skipped that UTC slot **without submitting a duplicate
API job**. The original independent API job then finished `completed`
using real Kopia. Thus, an interrupted scheduler claim cannot be equated
with failed underlying storage work. Status ledger and API job journal
contained no source path or bearer token. Output:

`PASS: killed scheduler after durable claim and running API job`

`PASS: restart marked uncertain claim interrupted without duplication`

`PASS: original real Kopia snapshot finished independently`

`PASS: private ledger/journal contain no token or source paths`

The script exited **0** and removed the temporary encrypted repository,
private policy, token, ledger, and test binaries. The real API service was
terminated by the test's own cleanup. No systemd timer, VPS service, cloud
remote or production backup was changed. This verifies an isolated
scheduler-process kill and skip semantics, **not** a full host crash,
power failure, recovery/retry protocol, restored application data or
multi-host distributed scheduling.


## Read-only schedule status — independent privacy and restart regression

The opt-in Linux schedule CLI now supports `-show-status`, which reads
only the private scheduling ledger, without a policy file or token and
without submitting jobs. New Go race tests exercise owner-only private
permissions, strict state-schema/identifier validation, unsafe modified
state rejection, and unchanged `claimed` status across a read-only
inspection. A normal exclusive scheduler restart still reconciles the
same claimed entry to `interrupted` without replay.

The real-Kopia disposable `scripts/smoke-scheduler.py` was expanded to
invoke this mode **without** a token-file argument, confirm the expected
completed policy IDs and absence of disabled policies, source paths and
the API token in its output, and assert the ledger bytes were unchanged.
The script reported:

`PASS: read-only schedule status inspection left state unchanged`

It also completed two encrypted snapshots, a structural verification, and
the existing repeated-invocation no-duplicate checks. The separate
`scripts/smoke-scheduler-crash.py` was rerun after stricter record
validation: it again passed scheduler SIGKILL, nonduplicating restart,
and independent completion of the original real Kopia API job.

Both isolated Linux tests exited **0**, used only private temporary
repositories, and cleaned up. These checks do not establish a
production GUI, authenticated remote status API, or cloud recovery.
